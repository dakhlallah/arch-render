# Output and Deliverables Standards

Use these standards when the user requests a professional project package, report, schedule, board,
technical draft, presentation, portfolio output, or client-facing handoff. Apply `core-policies.md`,
`project-leadership-roadmap.md`, and the specialist module governing each selected deliverable.

## Select the deliverable package

Honor the explicit request first. Then determine the smallest complete set of supporting deliverables
that makes the result immediately usable for the stated project stage and audience. Do not generate
every possible artifact on every response, bury a simple answer in a full report, or imply that an
unrequested package is complete. State:

```text
Primary deliverable:
Audience and decision it supports:
Project, stage, source revision, and status:
Included supporting deliverables:
Excluded or deferred deliverables and why:
Required professional verification:
```

When sources are insufficient, provide a clearly labeled template, partial schedule, issue register,
or missing-information request instead of inventing content. Do not claim an artifact was generated,
rendered, measured, coordinated, approved, or attached unless it actually was.

## Deliverable routing

Generate only evidence-supported items and load the named specialist rules:

- **Executive design summary, review report, recommendations, and client notes** — summarize the
  decision, findings, priorities, trade-offs, approvals, and next actions; use stable issue IDs.
- **Material and finish boards, material specifications, and color palettes** — use
  `material-reference-spec-mode.md`; separate observed finishes, approximate matches, proposals, and
  verified product data. Use real approved imagery and product sources, never fabricated samples.
- **FF&E schedules and styling packages** — use `furniture-styling-object-curation.md`; distinguish
  approved items from proposals and verify dimensions, availability, price, and performance.
- **Lighting plans or schedules** — use `technical-design-engineering-copilot.md`; label them
  conceptual unless supported and approved by the responsible lighting and electrical professionals.
- **Door and window schedules, specifications, and quantity estimates** — use
  `project-lifecycle-documentation-copilot.md`; preserve source marks, measurement logs, revisions,
  `TBD` fields, and the approximate-takeoff boundary.
- **Conceptual MEP layouts** — use `technical-design-engineering-copilot.md` and
  `technical-coordination.md`; never present them as engineered, coordinated, compliant, or
  construction-ready drawings.
- **Camera shot lists and rendering prompts** — use `architectural-camera-director.md`,
  `prompt-recipe.md`, and preservation rules. Plan only source-supported views and separate free prompt
  work from paid generation.
- **Presentation boards** — use `production-modes.md` and real supplied or approved assets. Apply
  `scripts/board.py` for deterministic boards when appropriate; do not fabricate drawings, project
  facts, credits, awards, metrics, or unseen views.
- **Architectural portfolios, competition booklets, publications, and editorial case studies** — use
  `portfolio-content-generator.md`; curate only relevant evidence-supported chapters, generate a
  unified editorial system and source-traceable section cards, and verify any produced file page by page.

If the user requests a native CAD, BIM, lighting, or MEP artifact and no compatible authoring tool is
available, provide a professional brief, annotated concept, schedule, or handoff specification rather
than pretending to create the native file.

## Client-ready structure

Match terminology, detail, and format to the audience while preserving technical precision. Use:

1. title, project, date, revision, author/status, and intended use;
2. executive summary and decision required;
3. scope, authoritative sources, and exclusions;
4. observations and verified facts;
5. recommendations with rationale, trade-offs, priority, owner, and dependencies;
6. assumptions, unknowns, missing information, and professional-verification items;
7. schedules, boards, drawings, prompts, or appendices with stable IDs and source references;
8. QA status, approvals required, and next logical deliverables.

Keep writing concise, professional, and internally consistent. Use clear hierarchy, legible tables,
consistent units, legends, naming, revision codes, and page numbering. Use clean grids, restrained
typography, adequate whitespace, aligned graphics, and captions that state source and status. Use
deterministic document, spreadsheet, presentation, or layout tools for artifacts when available; use
image-generation tools only for images.

## Deliverable QA and handoff

Before delivery verify:

- the artifact answers the requested decision and suits its audience and stage;
- every project fact, measurement, quantity, image, product, and requirement is traceable;
- approved design and revision locks remain unchanged;
- terminology, tags, units, schedules, cross-references, filenames, and page order are consistent;
- assumptions, gaps, exclusions, confidence, and `Requires verification` items are visible;
- regulated or contractual drafts carry the correct professional-review boundary;
- every promised file exists, opens, and is visually inspected when the available tools permit;
- proposed next deliverables are useful, non-duplicative, and not described as authorized work.

Conclude substantial work with the delivered items, validation status, unresolved inputs, and the next
one to three logical deliverables ordered by dependency and value. Propose them proactively, but obtain
authorization before paid calls, external uploads, purchases, regulated work, or scope expansion.

